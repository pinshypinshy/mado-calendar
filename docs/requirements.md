# 要件定義書：窓カレンダー（カレンダー共有アプリ）

最終更新：2026-11-15
この文書は、実装を担当する Claude Code にそのまま渡すことを想定している。旧「引き継ぎ\_カレンダー共有アプリ.md」の内容はすべてこの文書に統合した。

---

## 0. 概要

### 0.1 目的

- アプリの名前は「窓カレンダー」。画面・ホーム画面のアイコン名・Google の同意画面など、利用者に見える名前はすべてこれにする。ドメインやプログラム上の名前（`mado-cal`、`mado-calendar`）はそのままにする。
- 運営者が許可した数人のオーナーが、それぞれ自分の Google カレンダーを、自分が招待した閲覧者（家族など）に**閲覧専用**で見せる。
  - 最初のオーナーは運営者自身で、運営者のカレンダーを家族に見せることが当初の目的。
- 閲覧者ごとに見せる予定と見せ方を細かく制御し、UI も自由に作る。

### 0.2 Google 標準の共有機能を使わない理由

- 閲覧者ごとに表示範囲を変えたい。
- UI を自由に作りたい。
- 閲覧専用で共有すると、予定の色が見えない（単色で表示される）。

### 0.3 スコープ

- 閲覧者は予定を見るだけで、編集はできない。アプリからカレンダーに書き込む機能は作らない。
- ウィジェットとプッシュ通知は作らない。
- オーナーになれるのは、運営者が許可した Google アカウントだけにする。誰でも登録できる公開サービスにはしない（Google の審査を受けないため、オーナーは合計100人までという制限がある。7.4 を参照）。

## 1. 用語

| 用語       | 定義                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 運営者     | アプリを運営する人。1人のみ。オーナーの追加・削除ができる。運営者自身もオーナーとして使える                                    |
| オーナー   | 自分の Google カレンダーを共有する人。運営者が許可した Google アカウントでログインし、管理画面を操作する                      |
| 管理画面   | オーナー（と運営者）が使う画面。オーナーは自分のカレンダーと閲覧者だけを扱う                                                 |
| 閲覧者     | オーナーから閲覧者 ID を発行された人（父、母、友人など）。1つの閲覧者 ID は1人のオーナーに属する。Google アカウントは使わない |
| 閲覧者 ID  | 閲覧者1人につき1つ発行する、推測できない文字列。これを入力すると表示画面に入れる（「ログイン」ではなく「参加」という考え方） |
| 招待 URL   | 閲覧者 ID を含む URL。タップするだけで参加できる                                                                             |
| 表示レベル | 予定をどこまで見せるか。「詳細／カテゴリ／予定あり／非表示」の4段階（3.4 を参照）                                            |
| 表示ルール | 閲覧者ごとに、「カレンダー×ラベル」の組み合わせに表示レベルを割り当てる設定                                                  |
| 個別設定   | 閲覧者ごとに、特定の予定1件（または繰り返し予定のシリーズ）に表示レベルを割り当てる設定                                      |
| `#` ルール | タイトルが半角の `#` で始まる予定は、個別設定の初期値を「非表示」にするルール                                                |
| カテゴリ名 | 「カテゴリ」レベルなどで閲覧者に見せる予定の分類名（3.4 を参照）                                                             |

## 2. 前提・制約

- 閲覧者は全員 iPhone を使う。
- 提供形態は Web アプリとし、iPhone のホーム画面に追加して使う前提とする（PWA）。ネイティブアプリは作らない。
  - 将来 iOS アプリを追加できるよう、API は画面から独立させておく。
- 最優先で動作を検証する環境は、iPhone の Safari と、ホーム画面に追加した Web アプリの2つ。
- スマホでの表示に対応することは必須。
- タイムゾーンは Asia/Tokyo 固定。
- UI の言語は日本語。
- ドメインは `mado-cal.yuki-hiraishi.com`。
- 技術スタックは 8章を参照。**運用費は0円が必須**（Cloudflare の無料プランだけで動かす）。

## 3. 機能要件：オーナー

3.1〜3.9 はオーナーごとの機能で、オーナーは自分のデータだけを扱う（7.6 を参照）。運営者だけの機能は 3.10。

### 3.1 ログイン

- Google アカウントでログインする。
- 管理画面に入れるのは、運営者と、運営者がオーナーとして許可したメールアドレス（3.10）だけにする。
- ログアウトボタンを押したら、押し間違えでログアウトしないよう、本当にログアウトするかを確認する。
- 運営者のメールアドレスは、Workers の Secret（`OPERATOR_EMAIL`）で決める。リポジトリには書かない。
- 認証ライブラリ（Auth.js、Better Auth など）は使わず、Google の OAuth を自前で実装する。ログインと、カレンダーを読むためのリフレッシュトークンの取得（7.4）を、同じ処理で済ませるため。

### 3.2 対象カレンダーの選択

- オーナーのアカウントにあるカレンダーの中から、アプリで扱うものを選べるようにする。
- 例：運営者の場合は、メインカレンダーと授業カレンダー。

### 3.3 閲覧者の管理

- 閲覧者を追加できる。項目は表示名（例：「家族」「友人」）。
- 追加すると閲覧者 ID が発行され、招待 URL と一緒に表示される。
- 閲覧者 ID と招待 URL は、管理画面でいつでも再表示できる（そのため、ID はハッシュ化せずに暗号化して保存する。7.2 を参照）。
- 閲覧者 ID は、いつでも無効化・再発行できる。
  - 無効化すると、その閲覧者がすでに参加している端末も、すべて表示できなくなる。
  - 再発行すると、古い ID は使えなくなる。
- 閲覧者ごとに、最終閲覧日時を表示する（ID が漏れたことに気づくため）。
- 設定のコピー：ある閲覧者の設定一式を、別の閲覧者にコピーできる。コピーするのは、表示ルール、個別設定、閲覧者ごとのカテゴリ名、期間制限、週の開始曜日の初期値。

### 3.4 表示ルール（カレンダー×ラベル）

- 閲覧者ごとに、「カレンダー×ラベル」の組み合わせそれぞれに、以下の4段階から表示レベルを設定する。

| 表示レベル | 閲覧者に見える内容               | 色         |
| ---------- | -------------------------------- | ---------- |
| 詳細       | タイトル、日時、カテゴリ名       | ラベルの色 |
| カテゴリ   | 日時、カテゴリ名                 | ラベルの色 |
| 予定あり   | 日時だけ（表示上は「予定あり」） | グレー     |
| 非表示     | 何も表示しない                   | ―          |

- カテゴリ名の決め方（上にあるものほど優先する）：
  1. 閲覧者ごとの上書き：管理画面で、閲覧者ごとに、ラベルの表示名を上書きできる。上書きした場合はそれを使う。
  2. 全員共通の上書き：管理画面で、ラベルごとに、全閲覧者向けの表示名を上書きできる。
  3. どちらも上書きしていなければ、ラベルの名前を使う。
  4. ラベルの名前が空欄の場合や、ラベルのない予定は、カレンダーの名前を使う。
- 閲覧者ごとの上書きを空欄に戻すと、全員共通の名前（2〜4 で決まる名前）に戻る。
- ラベルのない予定は、「ラベルなし」という1つの行として設定できるようにする。
- 初期値：
  - まだ設定していない組み合わせ（新しく作ったラベルやカレンダーを含む）は「非表示」。
  - ラベルのない予定も「非表示」。
- 管理画面の表示ルールは、カレンダーごとに折りたためるようにする。閲覧者の画面を開いたときは、すべて閉じた状態にする。閉じていても、カレンダー名の横に表示レベルごとの件数を出す（0件のレベルは出さない）。
  - 理由：カレンダーやラベルが増えると一覧が長くなり、目的のカレンダーを探しにくくなるため。件数を出すのは、開かなくても、そのカレンダーをどれくらい見せているかが分かるようにするため。

### 3.5 個別設定（予定ごと）

- 管理画面で予定の一覧またはカレンダーを表示し、予定を選んで、閲覧者ごとに表示レベルを設定できる。
- 選べる値は、「ラベルに従う／詳細／カテゴリ／予定あり／非表示」の5つ。
- 繰り返し予定では、設定する範囲を「この回のみ」と「シリーズ全体」から選べる。初期値は「シリーズ全体」。
- 初期値：
  - 通常の予定は「ラベルに従う」。
  - `#` ルール：タイトルが半角の `#` で始まる予定は、全閲覧者について「非表示」。オーナーは、閲覧者ごとに別の値へ変えられる。全角の `＃` は対象外とする。

### 3.6 期間制限

- 閲覧者ごとに、期間制限の有無を選べる。
- 制限を付ける場合は、過去と未来の範囲を別々に指定する。
  - 例：過去は制限なし、未来は3か月先まで。
  - 例：過去1か月、未来3か月。
- 範囲外の予定はサーバーから返さない。閲覧画面でも、範囲外へは移動できないようにする。

### 3.7 週の開始曜日（初期値）

- 閲覧者ごとに、週の開始曜日（日曜または月曜）の初期値を設定する。
- 閲覧者は、自分の画面でこれを切り替えられる（4.4 を参照）。

### 3.8 プレビュー

- 閲覧者を選ぶと、その閲覧者に見えている画面を管理画面上で確認できる。
- 表示には、閲覧者用の画面と同じサーバー側の判定ロジックを使う（プレビュー専用のロジックを別に作らない）。

### 3.9 オーナーの表示名

- オーナーは、自分の表示名（例：「山田」）を設定できる。閲覧者が複数のオーナーを切り替えるとき（4.6）に表示する。
- 初期値は空欄。空欄のときは、閲覧者の画面に「（名前未設定）」と表示する。メールアドレスは閲覧者に見せない。

### 3.10 オーナーの管理（運営者のみ）

- 運営者は、管理画面で、オーナーとして許可する Google アカウントのメールアドレスを追加・削除できる。
- 追加したアドレスの人が Google でログインすると、オーナーとして使い始められる。最初のログインで、カレンダーへのアクセスを許可してもらう。
- オーナーの一覧には、メールアドレス、表示名、最終ログイン日時を表示する。
- オーナーを削除すると、そのオーナーのデータ（閲覧者、表示ルール、個別設定、カテゴリ名、対象カレンダー、トークン、キャッシュ、セッション）をすべて消す。そのオーナーの閲覧者は、すぐに表示できなくなる。
- 運営者自身は削除できない。
- 運営者が管理画面で見られる、ほかのオーナーの情報は、上の一覧の項目だけにする。ほかのオーナーの予定・閲覧者・設定は、管理画面のどこにも表示しない。運営者の管理画面に出る予定や閲覧者は、運営者自身のものだけ。
  - 例：運営者がオーナー B を追加しても、運営者の「オーナー」の一覧に出るのは、B のメールアドレス・表示名・最終ログイン日時だけ。B の予定や、B が招待した閲覧者は見えない。

## 4. 機能要件：閲覧者

### 4.1 参加の流れ

1. 閲覧者は、招待 URL を開くか、ID 入力画面に閲覧者 ID を入力する。
2. サーバーが ID を検証し、正しければ参加状態を記録する Cookie を発行する（7.3 を参照）。
3. 参加すると表示画面に移る。同じ端末で次に開いたときは、入力なしで表示画面が開く。

- 閲覧者 ID は、1人のオーナーに属する。
- 1台の端末で、複数のオーナーの閲覧者 ID に参加できる（例：ある閲覧者が、オーナー A とオーナー B の両方に招待された場合）。参加済みの状態で別の閲覧者 ID を使うと、参加しているオーナーが増える。

### 4.2 ホーム画面への追加の案内

- ホーム画面に追加された Web アプリとして起動していない場合（standalone でない場合）は、「Safari で開いて、ホーム画面に追加してください」という案内を出す。
- LINE などのアプリ内ブラウザで開かれた場合は、Safari で開き直すよう案内する。
- ホーム画面に追加した Web アプリを開いて、まだ参加していない状態であれば、ID 入力画面を出す。
  - 理由：ホーム画面に追加した Web アプリのデータは Safari と分離されている。iOS 17.2 以降は、ホーム画面に追加した時点で Safari の Cookie がコピーされるが、それ以降は同期されない。そのため、追加したあとに参加し直した場合や、古い iOS では、もう一度参加が必要になる（10章 #3）。

### 4.3 表示画面

- 週表示・月表示を切り替えられる。開いたときは、今日を含む月の月表示にする。
- 前の期間・次の期間・今日へ移動できる（期間制限の範囲内に限る）。
- 予定名が枠に入りきらないときは、点々（…）を付けずに枠の端で切り、入るところまで表示する。
  - 理由：月表示のマスは狭く、点々が1文字分を取ると、3文字ほどしか読めなくなるため。
- 週表示：
  - 0〜24時を表示し、縦にスクロールできる。
  - 開いたときに上端に来る時刻は、次のルールで決める。
    - 今日を含む週を表示しているとき：現在時刻の2時間前。2時間前が前日になる場合（0〜1時台）は 0:00。
    - 今日を含まない週を表示しているとき：8:00。
  - 現在時刻を示す線を表示する。
  - 終日の予定と、複数日にまたがる予定は、上部の帯に表示する。
- 月表示：
  - 各日の予定を、表示レベルに応じた形で、マスの高さに入るだけ表示する。入りきらないときは、最後の1行に残りの件数だけを出す。
    - 理由：マスの高さは、端末の画面の高さと、その月の週の数（4〜6週）で変わる。件数を固定すると、背の高い端末では空きが出て、6週の月でははみ出すため。
  - 日付をタップすると、その日の予定一覧を表示する。
- 予定をタップすると詳細を表示する。表示する内容は、その閲覧者の表示レベルで見せてよい範囲に限る（3.4 の表）。
- `#` ルールの対象だが表示を許可した予定は、タイトル先頭の `#` を取り除いて表示する。

### 4.4 閲覧者自身による設定

- 週の開始曜日（日曜または月曜）を切り替えられる。設定はサーバー側に閲覧者ごとに保存し、端末が変わっても引き継がれるようにする。

### 4.5 更新

- 更新ボタンを置く（6章）。表示の切り替えなどの操作ボタンの行の右端に置く。

### 4.6 オーナーの切り替え

- 複数のオーナーに参加している場合は、画面の上部で、表示するオーナー（表示名）を切り替えられる。予定は、選んだオーナーの分だけを表示する（複数のオーナーの予定を1つの画面に重ねない）。
- 次に開いたときは、最後に選んだオーナーを表示する。選択は、参加状態と同じくサーバーが発行する Cookie で覚える。
- 最後に選んだオーナーを表示できない場合（そのオーナーに無効化された、オーナーが削除された、Cookie が消えた、など）は、残っているオーナーのうち最初に参加したオーナーを表示する。
  - 例：ある閲覧者が「A」と「B」に参加していて、最後に「B」を見ていた。その後、B がその閲覧者 ID を無効化した場合、次に開くと「A」を表示する。
- ID 入力画面を開いて、別のオーナーの閲覧者 ID を追加できる。
- 画面の右上の「退出」で、表示中のオーナーへの参加から退出できる。
  - 押し間違えで退出しないよう、退出する前に必ず確認を出す。
  - 外れるのはこの端末の参加だけ。閲覧者 ID は有効なままなので、同じ招待 URL か ID でまた参加できる。
  - 退出したあとは、ほかのオーナーにも参加していれば、そのうち最初に参加したオーナーを表示する。どこにも参加していなければ、ID 入力画面を出す。

## 5. 表示判定ロジック

ある予定 `e` を閲覧者 `v` に見せるときの表示レベルは、次の順で決める。判定はすべてサーバー側で行う。

```
function resolveLevel(e, v):
  # 1. 期間制限
  if v.periodLimit.enabled and e が v の許可期間の外にある:
    return 非表示

  # 2. 個別設定（「この回のみ」を「シリーズ全体」より優先する）
  o = 個別設定(v, e.instanceId) ?? 個別設定(v, e.recurringEventId ?? e.id)
  if o が存在し、o != ラベルに従う:
    return o
  if o == ラベルに従う:
    return 表示ルール(v, e.calendarId, e.labelId ?? ラベルなし) ?? 非表示

  # 3. # ルール（個別設定が未設定のときの初期値。半角 # のみ）
  if e.title.startsWith("#"):
    return 非表示

  # 4. 表示ルール
  return 表示ルール(v, e.calendarId, e.labelId ?? ラベルなし) ?? 非表示
```

- 「非表示」と判定された予定は、レスポンスに含めない（件数も含めて、存在が分からないようにする）。

## 6. データ取得と更新

| 項目                 | 仕様                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| サーバー側キャッシュ | Google から取得した予定を、オーナーごとに5分間保持する。閲覧者ごとの絞り込みは、キャッシュから取り出したあとに行う。保存先は D1 または Cache API（KV は無料枠の書き込み回数が少ないため使わない。8.2 を参照） |
| 閲覧画面の自動更新   | 画面を表示している間は5分ごとに取り直す。タブやアプリに戻ってきたとき（visibilitychange／focus）にも取り直す                                                                                  |
| 更新ボタン           | キャッシュを使わずに Google から取り直す。読み込み中はボタンを押せないようにして連打を防ぐ。サーバー側でも閲覧者ごとに5秒の間隔制限を付け、制限中はキャッシュを返す（閲覧者には知らせない） |
| リアルタイム反映     | 作らない（Google からの変更通知の仕組みは使わない）                                                                                                                                           |

## 7. 非機能要件

### 7.1 返すデータの制限

- 閲覧者に返すのは、表示レベルに応じた項目（タイトル、日時、カテゴリ名、色）だけにする。
- 説明欄、場所、参加者、会議リンク、添付ファイルなどは、どの表示レベルでも返さない（説明欄に URL や連絡先が入っているため）。
- 「カテゴリ」と「予定あり」のレベルでは、タイトルを返さない。

### 7.2 閲覧者 ID

- 推測できないランダムな文字列にする。手で入力することも想定し、紛らわしい文字（0/O、1/l/I など）を除いた英数字で、十分な長さにする（長さは実装時に決める。目安は80ビット相当以上）。
- 管理画面で再表示するため、ID はハッシュ化せず、暗号化して D1 に保存する。照合用に、ハッシュ値も別に保存してよい。
- 暗号鍵は、Workers の Secret に保存し、コードやリポジトリには含めない。
- ID 入力の失敗回数に制限をかける（総当たり対策。例：同じ IP から10分間に10回失敗したら一時的にブロックする）。
- 無効化・再発行はすぐに反映する。

### 7.3 参加状態の保持（Cookie）

- 参加状態は、サーバーが Set-Cookie ヘッダーで発行する Cookie で保持する。属性は HttpOnly／Secure／SameSite=Lax。
  - JavaScript で書き込む Cookie や localStorage は使わない（Safari では、7日間そのサイトで操作がないと削除されるため）。
- 画面と API は、同じ Worker から同じドメインで配信する（Safari 16.4 以降は、Cookie を発行したサーバーの IP がサイトと無関係だと、有効期限が7日に制限されるため）。
- Cookie の有効期限は長め（例：最大400日）にし、アクセスのたびに延長する。
- Cookie の値には、閲覧者 ID そのものではなく、サーバー側で管理するセッションの識別子を入れる。閲覧者 ID を無効化・再発行したら、そのセッションもすべて無効にする。

### 7.4 オーナーの OAuth トークン

- 各オーナー本人の OAuth トークンで、そのオーナーのカレンダーを読む。トークンはオーナーごとに保存する。予定の色は、オーナーと編集権限を持つ人にしか見えないため。サービスアカウントや iCal では色を取れない可能性が高い（推測で、検証はしていない）。
- スコープは、読み取り専用の最小限にする。
- リフレッシュトークンは、暗号化して D1 に保存する。
- OAuth 同意画面は「本番（In production）」にする。テスト中のままだと、リフレッシュトークンが7日で失効する。
- Google の審査は受けない。カレンダーの読み取りは「機密性の高いスコープ」なので、未審査のアプリにログインできるのは、アプリの全期間で合計100人まで。オーナーはこの範囲に収める（閲覧者は Google でログインしないので数えない）。ログインの際には「確認されていないアプリ」という警告が出る。
- リフレッシュトークンは、同意画面を本番に切り替えたあとに取得する。テスト中に発行したトークンは7日で失効する。
- 同意画面を本番にするには、ホームページとプライバシーポリシーの URL が必要（Google の要件）。ホームページは `https://mado-cal.yuki-hiraishi.com/`、プライバシーポリシーは `https://mado-cal.yuki-hiraishi.com/privacy.html`（`public/privacy.html`）とし、承認済みドメインに `yuki-hiraishi.com` を登録する。

### 7.5 スマホ対応

- iPhone での表示を前提にしたデザインにする（モバイルファースト）。
- ホーム画面に追加して使えるよう、Web App Manifest とアイコンを用意する。
- 管理画面も、閲覧画面とは別のアプリとしてホーム画面に追加できるようにする。`/admin` から追加すると、管理画面が開くアイコン（名前は「窓カレンダー 管理」、色は閲覧画面と変える）になる。
- 管理画面のメニューは「閲覧者」「予定」「設定」の3つにする。それぞれアイコンと名前を出す。
  - 画面の幅が 768px 未満のときは、画面下に固定するタブバーにする。768px 以上のときは、左に固定するサイドバーにする。
  - 「設定」は項目の一覧にし、選ぶとその画面に移る。項目は「カレンダー」（対象カレンダーの選択とキャッシュ）、「カテゴリ名」（全員共通のカテゴリ名）、「アカウント」（オーナーの表示名とログアウト）、「オーナー」（運営者にだけ出す）。
  - 今いるメニューをもう一度押すと、そのメニューの最初の画面（一覧）に戻る。
  - 「閲覧者」の画面は、見出しの行の右端に＋ボタンを置く。押すと画面の中央にダイアログを出し、表示名を入力させる。表示名が空のあいだは追加できない。一覧の各行は、左端に人のアイコンを置き、その右に表示名と最終閲覧日時を出す。
  - 「カテゴリ名」の画面は、カレンダーごとに折りたためるようにする。開いたときはすべて閉じた状態にし、閉じていても、カレンダー名の横にラベルの件数と、上書きしている件数を出す。
  - 理由：よく使うのは「閲覧者」と「予定」で、ほかの画面は最初の設定やまれな変更にしか使わない。すべてを同じ並びに置くと、iPhone の幅に入りきらず、よく使う画面も探しにくくなるため。

### 7.6 オーナー間のデータの分離

- すべてのデータ（閲覧者、表示ルール、個別設定、カテゴリ名、対象カレンダー、トークン、キャッシュ、セッション）を、オーナーごとに分けて保存する。
- オーナーは、自分のデータだけを読み書きできる。ほかのオーナーの閲覧者などの ID を指定しても、存在しないものとして扱う（「見つからない」と返し、存在するかどうかも分からないようにする）。
- 閲覧者は、参加しているオーナーのデータだけを見られる。
- 分離は、運用上の約束ではなく、コードの構造で守る（データを読み書きする入口で、オーナーを固定する）。あわせて、ほかのオーナーのデータに届かないことをテストで確かめる。

### 7.7 運営者によるデータへのアクセス

- データの置き場所（Cloudflare）は運営者のアカウントなので、運営者は、ダッシュボードやコマンドでデータベースを直接開けば、ほかのオーナーのデータ（キャッシュに入っている予定のタイトルなど）を読めてしまう。これは仕組み上防げない。
- そのため、管理画面では見られないようにしたうえで（3.10）、プライバシーポリシー（`public/privacy.html`）に、このことと、「運営者は、障害への対応など必要な場合を除き、オーナーのデータを見ない」ことを正直に書く。

## 9. 検証済みの API・ラベル仕様

2026-11-14 に検証。Web 版のビルドは `calendar.web_20261110.05_p0`。

- 色番号（colorId 1〜11）を持てるラベルは、カレンダーごとに最大11個。新しい13色や任意の色のラベルは colorId を持たない。
- colorId は色コードではなく、ラベル自体に結び付いている。ラベルの名前や色を変えても colorId は保たれる。
- colorId を持つラベルを削除すると、その番号は空きになる。削除前にそのラベルが付いていた予定は colorId が外れ、元に戻らない。→ **従来の11ラベルは削除しない。**
- colorId を持たないラベルの予定は、list_events／get_event ではラベル情報が返らない。
- 公式 API では、カレンダーの `labelProperties.eventLabels`（ラベル一覧。`id`、`name`、`backgroundColor`）と、予定の `eventLabelId` でラベルを扱える（2026-07-07 に正式対応）。書き込みには `eventLabelVersion=1` が必要。**アプリはこちらを使って、ラベル ID と名前・色を対応付ける。**読み取りでは、`eventLabelVersion=1` を付けなくても `calendar.readonly` で `eventLabelId` が返る（2026-11-15 に運営者のカレンダーで確認。10章 #1）。ラベル ID が返らない予定は colorId で判定する。
- 予定を別のカレンダーへ移すと、色と通知設定がリセットされる。
- MCP コネクタでは colorId しか指定できず、予定を別のカレンダーへ移す機能もない。
- 詳細な仕様は、運営者の Claude 環境にある google-calendar スキルにまとめてある（実装環境から参照できるとは限らない）。
