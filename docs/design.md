# 設計

要件は [requirements.md](requirements.md) にある。この文書には、要件を満たすために選んだ作り方と、その理由を書く。

---

## 1. 構成

1つの Worker から、画面（静的アセット）と API を同じドメインで配信する（要件 7.3）。`wrangler.jsonc` の `assets.run_worker_first` で、`/api/*` と `/auth/*` だけを Worker のコードに渡し、それ以外は画面のファイルを返す。

| ディレクトリ | 役割 | 依存してよい先 |
| --- | --- | --- |
| `src/shared/` | API の型、日付の計算。画面と Worker の両方から使う | なし |
| `src/worker/domain/` | 表示判定、期間制限、カテゴリ名、閲覧者 ID など、外部に依存しないロジック | `shared`、`domain` |
| `src/worker/ports.ts` | 外部とやり取りする部分のインターフェース（D1、Google、時計、乱数、暗号） | `shared`、`domain` |
| `src/worker/services/` | ユースケース（参加、予定の絞り込み、閲覧者の管理、ログインなど） | `shared`、`domain`、`ports`、`lib` |
| `src/worker/adapters/` | ports の実装（D1、Google、Web Crypto、フェイク） | すべて |
| `src/worker/http/` | HTTP のルーティング（Hono） | `services` など |
| `src/worker/container.ts` | 依存の組み立て。実装を選ぶのはここだけ | すべて |
| `src/web/` | 画面（React） | `shared`、`web` |

依存の向きは [src/architecture.test.ts](../src/architecture.test.ts) で確かめている。破るとテストが失敗する。
また、Worker と画面は別々の tsconfig で型を確かめる（`tsconfig.worker.json` には DOM の型がなく、`tsconfig.web.json` には Workers の型がない）。

## 2. 依存性の注入（DI）

- サービスはコンストラクターで ports を受け取る。`new` で実装を作るのは `container.ts` だけ。
- `assembleServices(infra)` が組み立てを担い、本番（`buildServices(env)`）とテスト（`src/worker/testing/harness.ts`）が同じ関数を使う。テストでは、時計・乱数・Google だけを差し替え、D1 はローカルの本物（wrangler の `getPlatformProxy`）を使う。
- 画面も同じ考え方で、`CalendarScreen` はデータの取り出し口（`CalendarFeed`）を受け取る。閲覧画面は閲覧者用の API を、管理画面のプレビューはプレビュー用の API を渡す。こうして、プレビューが閲覧画面と同じ部品・同じサーバー側の判定を使うようにしている（要件 3.8）。

## 3. フェイクモード

`CALENDAR_SOURCE=fake` のとき、Google の代わりに `src/worker/adapters/fake.ts` を使う。

- カレンダー：日付から決まる予定を返す（繰り返し、終日、複数日、日をまたぐ予定、重なる予定、`#` の予定、ラベル ID のない予定を含む）。
- ログイン：Google にリダイレクトせず、`ADMIN_EMAIL` でそのままログインする。
- 誤って本番で有効にしても動かないよう、ホスト名が `localhost`・`127.0.0.1`・`[::1]` 以外なら 500 を返す（`src/worker/index.ts`）。

## 4. 主な設計判断

### 4.1 ラベルの判定（要件 3.4、10章 #1）

予定のラベルを、次の順で1つのキー（`labelKey`）にする。

1. `eventLabelId` があれば `label:<ID>`
2. なければ、colorId があれば `color:<番号>`
3. どちらもなければ `none`（ラベルなし）

読み取りで `eventLabelId` が返るかは、公式資料に書かれておらず、まだ確かめていない。返らない場合でも colorId で動くよう、両方に対応した。管理画面では、`color:` の行を「予備」として折りたたんで出す（Google のラベルが1つもないカレンダーでは最初から開く）。
実機で確かめたあと、`eventLabelId` が返ると分かれば、`color:` の行を消して画面を簡単にできる。

### 4.2 個別設定のキー（要件 3.5）

- 「この回のみ」：予定の ID（繰り返し予定では回ごとに違う）
- 「シリーズ全体」：`recurringEventId`（繰り返しでない予定は予定の ID）

インスタンス ID が編集後も変わらないかは未確認（10章 #2）。

### 4.3 キャッシュ（要件 6章）

- 保存先は D1。テストでそのまま確かめられ、保存先を1つにまとめられるため。
- 単位は「カレンダー × 月」。週表示でも月表示でも、同じ月のキャッシュを使い回せる。
- Google からの取得に失敗したときは、古いキャッシュがあればそれを返す（Google の一時的な障害で画面が空にならないように）。ただし更新ボタンのときは、古いデータを最新と見せないよう、エラーを返す。
- 更新ボタンでは、予定に加えて、カレンダーの一覧・ラベル・色も取り直す。
- 1回のリクエストで取得できる期間は最大62日（月表示の最大6週が収まる長さ）。月をまたぐと最大3か月分を読むので、サブリクエスト数（無料プランは1回の処理につき50件）に収まるようにしている。

### 4.4 閲覧者 ID と招待 URL（要件 7.2）

- 紛らわしい文字（0/O、1/I/L）を除いた大文字英数字31種類 × 20文字（約99ビット）。入力時は大文字・小文字やハイフンを区別しない。
- 暗号鍵は Secret の `ENCRYPTION_KEY`（32バイト）1つ。HKDF で、暗号化用（AES-GCM）と照合用ハッシュ用（HMAC-SHA256）の2つの鍵を作る。同じ鍵を2つの用途に使わないため。
- 招待 URL は `https://<ドメイン>/join#<ID>`。ID を URL のフラグメント（`#` 以降）に入れる。フラグメントはサーバーに送られないので、アクセスログや LINE のリンクプレビューの取得で ID が漏れにくい。参加したら URL を `/` に置き換え、ホーム画面に追加したときの URL に ID が残らないようにする。
- LINE などのアプリ内ブラウザで招待 URL を開いた場合は、参加せずに「Safari で開く」よう案内する。「Safari で開く」で、ID を含む URL をそのまま Safari に渡すため。

### 4.5 セッション（要件 7.3）

- Cookie にはランダムなトークン（256ビット）を入れ、D1 にはその SHA-256 だけを保存する。
- 有効期限は400日。アクセスのたびに延長するが、D1 への書き込みを減らすため、延長は1日1回まで。
- `Secure` 属性は、ローカル開発（ホスト名が `localhost` など）のときだけ付けない。
- 本番のホストに http で来た Worker 宛てのリクエストは、https へ転送する（308）。画面のファイルは Worker を通らずに配信されるので、ゾーンの「Always Use HTTPS」も有効にする。
- `*.workers.dev` とプレビュー URL からは配信しない（`wrangler.jsonc` の `workers_dev` と `preview_urls`）。Cookie と招待 URL のドメインを1つにするため。

### 4.6 管理者のログイン（要件 3.1、7.4）

- Google の OAuth を自前で実装した。state と PKCE（S256）を使い、その値は有効期限10分の Cookie（パスは `/auth`）に入れる。
- ID トークンは、トークンエンドポイントから TLS で直接受け取るので、署名の検証は省いた（OpenID Connect Core 1.0 の 3.1.3.7 で許されている）。発行者と宛先（`aud`）は確かめる。
- 同意画面（`prompt=consent`）は、リフレッシュトークンをまだ持っていないときだけ出す。
- リフレッシュトークンが失効していたら（Google が `invalid_grant` を返したら）、保存していたトークンを消す。管理画面に「連携していません」と出て、次のログインで同意画面が必ず出るようにするため。
- Google のエラーの本文はログにだけ出し、利用者には返さない。
- スコープは `openid email https://www.googleapis.com/auth/calendar.readonly`。

### 4.7 CSRF 対策

Cookie の `SameSite=Lax` に加えて、書き込みのリクエスト（GET 以外）は `Origin` ヘッダーが同じオリジンのものだけを受け付ける。

### 4.8 閲覧者に返すデータ（要件 7.1）

- Google から取得する時点で、説明欄・場所・参加者などを取らない（`fields` パラメーターで絞る）。キャッシュにも入らない。
- 閲覧者に返す予定の ID は、レスポンスの中だけの連番（`e0`、`e1` …）。Google の予定 ID は返さない。

### 4.9 期間制限と一部だけ重なる予定

許可期間と少しでも重なる予定は返し、開始・終了時刻はそのまま返す（期間の境目で切り詰めない）。たとえば「未来0か月」の閲覧者にも、今日から始まる3日間の終日予定は、終了日まで見える。要件 3.6 の「範囲外の予定」を「期間とまったく重ならない予定」と解釈した。
